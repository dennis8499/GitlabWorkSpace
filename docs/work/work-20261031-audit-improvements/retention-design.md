# 操作收據保留與壓縮：後續設計草案

本輪僅完成量測及設計，不修改既有收據、刪除資料或啟用自動回收。`OperationReceiptFileStore` 依識別碼雜湊分桶，完成的讀取和寫入都可能留下收據；記憶體快取上限不限制磁碟成長。

## 必須保留的保證

- 已完成寫入的 `requestId` 與 `correlationId` 必須在重啟後仍可精確查詢，避免重送造成重複副作用。
- 未知結果與仍執行中的操作目前不寫入此檔案收據儲存；其獨立的狀態與對帳機制不能因壓縮而被清除或視為成功。只有明確對帳後才能依既有流程解除限制。
- 舊收據的 `kind` 為選填；無法確定性質時，保守視為寫入，不因缺少分類而回收。
- 讀取收據也可能被重新連線後的 UI 用於對帳；不能只因讀取無遠端副作用就立即刪除。

## 候選方案

先評估逐桶壓縮：逐行驗證現有記錄，對每個識別碼保留目前查詢會回傳的最後一筆；所有寫入識別碼及其關聯識別碼均保留。以同一磁碟的暫存檔寫入、完成同步後原子替換，並與現有讀寫佇列協調；中斷、空間不足或驗證失敗時保留原檔並停止該桶，不以空檔取代。此作法只去除重複記錄，**不會為唯一寫入識別碼提供容量上限**。

讀取收據的期限或數量上限需要先明確定義重播與重啟對帳契約，再提出獨立變更。若未能建立安全期限，繼續保留；不得依檔案修改時間刪除整桶，也不得將未知結果當作一般已完成收據。

## 後續驗證

在隔離資料上測試跨重啟的 request／correlation 查詢、重複識別碼、舊格式缺少 `kind`、讀寫同時進行、截斷／損壞記錄、磁碟空間不足、替換前後程序中斷與回復。比較壓縮前後查詢結果與檔案大小，並確認任何失敗均維持現有的寫入去重與未知結果保護。
