# 0.51.0

整合 GitlabWorkSpace 與 WorkflowKit 的任務執行、人工確認及成果保存流程。搭配 WorkflowKit 1.10.0，保留既有任務與外部 BMAD 的恢復及相容路徑。

## 任務與來源

- 從準備頁建立受管理工作區，在獨立 VS Code 視窗取得 owner／generation 後執行；舊視窗不能接續寫入或清理新 owner 的任務。
- 依帳號、站台與專案重用 Repo 快取。Issue 開發使用無 hardlink／alternates 的獨立 Clone，Wiki 與需求探索使用固定來源 archive。
- Wiki／Issue 的遠端來源以 GitLab metadata 核對；Group／Repo 需求探索使用本機已提交 HEAD，不包含未提交內容，也不因探索同步遠端。

## 產出與人工確認

- Wiki 先產生逐頁草稿，確認後新增或更新，保留人工頁面與衝突檢查、發布收據。
- 需求探索以 Codebase LLM Wiki 的 source-first 能力蒐集證據，再整理 BMAD 文件及 Issue 草稿；確認後才建立選定 Issue，逐張保存與核對發布結果。
- Issue 預設一般 Build；明確選用且通過同步子代理、sandbox Git 探測後才啟用 Build Auto。可採納多筆既有本機 Commit，要求任務提交標題含該 Repo 的 `(#IID)`，綁定提交清單、最終成果及驗證證據後才允許 Push 與 Draft MR。
- MR 可選 MergeReviewer 或 ReleaseReviewer，兩者從準備、偏好、runtime、報告到恢復分開辨識。各任務成果頁提供自己的報告發布入口；完整固定報告與來源版本核對後，由 Host 發布已確認正文。
- 修正冷啟動視窗尚無專案清單時的錯誤 Group 判定。無發布收據的已完成審查可透過唯讀 GET 對帳恢復；真正 pending／unknown 保持核對流程，不盲目重送。
- 手動複製僅提供需求探索／Issue 草稿及 MR 審查，由人工處理產出；Wiki 與 Issue 開發使用 App Server 流程。

## BMAD 與成果

- 五入口 `/goal`、`/plan`、`/build`、`/verify`、`/project`，以及開始明確變更、繼續既有工作、查看進度與下一步三個常用操作；`/goal` 同時負責智慧路由。
- CLI／Codex 聊天使用 `$wk-goal` 等五個 Skill 名稱。共用能力登錄表驅動畫面與提示詞，每階段讀取必要完整指引；Codex 自動提供的技能簡介維持原生行為。
- 成果依原 Group／Repo 持久索引。清理前驗證並保存完整成果；未推送 Commit 另外保存可還原資料，專案規則須預覽差異並確認後才套用。

## 驗證範圍

本機正式分項檢查包含 1,730 項單元通過、4 項略過，380 項介面行為、40 個 BDD 情境、VS Code Host 24 項通過／5 項未啟用，以及發行工具與打包驗證。首次完整 `all` 因啟動測試的總事件數斷言失敗；保留原紀錄，改以直接核對過期配額與 MCP 資料後，完整單元重跑及其餘正式分項補驗通過，沒有宣稱原單次 `all` 成功。

真實 App Server／sandbox／測試 GitLab 已驗證主要流程，包含一般 Build 的人工交付、本機 Build Auto、6 頁 Wiki、Issue 建立與兩種 Reviewer 報告留言及回讀。完整故障矩陣、所有手動 CLI／Chat 路徑與跨平台實機組合仍未全數驗完；兩份 Reviewer 報告是靜態審查。詳見[驗證紀錄](../work/work-20261114-task-workflows/verification.md)。

正式 Release 由 GitHub 完整 Windows／Python／VS Code 矩陣驗證後，提升相同的已驗證附件；本機產物不取代正式 CI 來源證據。
