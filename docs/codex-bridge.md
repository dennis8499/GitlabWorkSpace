# 使用 Codex 任務工作台

## 需求交接與驗收證據

任務保存來源需求快照、驗收條件及內容摘要；Issue 建立後仍以 GitLab Issue 作為正式需求。工作關聯由系統保存，既有 Issue、外部 MR、獨立 Reviewer 與本地 Wiki 都可直接使用。從已建立的 Issue 或已交付 MR 可點選下一步，沒有自動跨階段執行。

驗證命令可使用適用的 build、lint 或 test。最終檢查保留每次成功、失敗、中斷與缺證據的紀錄，並綁定來源、成果及核定設定。可修正的原生檢查失敗最多進行三輪本地實作與驗證（包含首次實作）；重啟不重置次數，相同成果反覆失敗可提前停止。缺依賴、權限、來源漂移及程序中斷須先處理，遠端送出結果不明仍只對帳。

沒有核定自動檢查命令的純文件變更，可選「人工驗收文件變更」：先開啟差異，再逐項勾選檢查。人工驗收不記成測試成功，之後仍須另行檢閱並確認 GitLab 交付。混合程式／設定變更不能使用此路徑。需求原已符合時，須有明確結論及實際核定檢查證據，人工確認後只發布摘要，不建立空 Commit 或 MR。

成果分開呈現需求逐條核對、檢查證據與審查結論；靜態 Release Report 不代表部署環境已驗證。匯出成果保存來源及失敗紀錄，歷史確認只供稽核，不授予新任務發布權限。

## 本地 Wiki

本地 Codebase Wiki 可離線查詢、建立／更新與檢查。查詢先讀現有 Wiki，必要時回查相關來源並揭露缺口，不自動全量掃描或更新。在 Group 根目錄選單一 Repo，來源只限該 Repo，成果保存在 Group 共用 `wiki/`；直接開啟單一 Repo 時，成果保存在該 Repo 的 `wiki/`。不向父目錄推定另一個工作區，也不搬移或合併既有 Wiki。

更新前保存 Wiki 基線，完成後由 Host 執行現有品質 helpers。Repo 的建立／更新入口檢查完整所選 Repo 的 coverage，Group 模式使用各 Repo 獨立的 coverage ledger；局部路徑更新只以本次範圍判定，明確選全 Group 才要求全 Group coverage。來源映射、既有人工備註區塊、追加式日誌與未授權刪頁受到核對；修改其他 Repo 或來源不明的既有頁面時保留成果並標示需要處理。未標記人工正文仍依既有 writer 的保留規則處理。Query／品質檢查的預設寫入範圍只有 helper runtime；更新只允許 Wiki 與 helper runtime，原始碼不列入寫入範圍。

相同固定提交可重用已驗證的來源 archive，但每個任務仍有獨立可寫成果。工作目錄 Wiki 使用實際來源內容判斷變更，不以相同 HEAD 推論內容未變。產生 GitLab Wiki 草稿及發布保持獨立操作。

## 新增任務與管理

可從 Issue、MR、專案或 Skills／BMAD 的執行按鈕開啟任務準備；自由任務可在 Codex 頁按「建立 Codex 任務」，或使用同名原生命令。首次準備保存需求、Repo、模型、思考強度、額外 Skills、測試入口及交付偏好。後續 GitLab 功能沿用同工作區、帳號、專案與功能的有效偏好，一鍵檢查並執行；缺資料或來源變更時展開準備頁。MR 審查與討論修正的偏好分開。必要 Skill 固定勾選，執行前核對啟用狀態、路徑與內容指紋。

新任務由目前開啟 Group／Repo 的 VS Code 視窗管理，可在同一工作台回答、續作、檢視差異及確認交付。任務摘要列出工作區根目錄、來源 Repo 與實際執行目錄；另窗瀏覽工作目錄是選用操作，不移轉任務控制權。既有獨立任務視窗仍沿原方式恢復，其他視窗只能讀取狀態。遠端交付一律先檢閱當次成果，確認綁定內容、提交歷史及測試證據；保存偏好與自動核准不代替確認。

GitLab 任務缺少本機 Repo 時會準備管理快取；已有本機副本先從本機複製物件，只有缺少必要來源才連 Git Server。缺少 WorkflowKit、登入或 Windows sandbox 時，使用檢查項目的修復入口，再按「重新檢查」。離開畫面或重新載入會保留內容；多視窗修改草稿時保留衝突供選擇。

未送出的訊息、一般問題／工具表單回答、MR 回覆及準備輸入，另依帳號與專案保存在本機。顯示保存完成後，即使關閉工作台或重新啟動 VS Code，也能恢復；密碼等秘密欄位只留在目前畫面記憶體。多視窗修改不同草稿可各自保存；同一筆內容發生衝突時保留兩份，供明確選擇或複製，不會用較晚抵達的舊內容覆寫。恢復草稿不會自動送出訊息、回答或發布。

重新檢查發現來源改變時，準備頁列出前後 SHA、目標 SHA、Issue 標題／更新時間及已選討論的變更提示；須明確確認更新的來源才能開始。重查相同版本不會清除尚未確認的差異，再次變更則重新要求確認。已停止且執行、清理、發布及訊息結果明確的 Issue／MR／Wiki 任務，可按「重新準備」另開草稿，保留需求、Repo、模型與返回位置，並以原任務來源比較；原任務及其他未完成草稿保留，也不會直接排入執行。已送出的任務仍使用既有固定來源及排隊前核對規則。

自由任務不需要 WorkflowKit，也可使用「將選取文字帶入 Codex 任務」。文字檔與選取區塊固定為送出時的快照，每項最多 32,000 字、合計最多 128,000 字及 10 項；送出前可預覽，其他 Repo 的檔案會被拒絕。

每個任務獨立保存模型與強度，後續傳送及恢復沿用選擇；對話分支繼承來源設定，重新同步的新 request 可重新選擇。Codex 頁的「模型與使用量」分別顯示任務設定與實際執行資訊。這些選擇不會修改全域 Codex 設定。

任務清單支援搜尋、狀態／Repo 篩選與顯示封存。「更多操作」提供重新命名、釘選、封存、排隊順序、診斷、對話分支及目標設定；封存只隱藏管理紀錄。對話分支建立獨立且暫停的自由任務，保留原對話，也不繼承原工作流程的發布權限。

任務列可直接刪除紀錄，或進入管理模式批次選取，每次最多 1,000 筆。執行中任務須先停止；確認視窗說明刪除範圍及成果位置，部分失敗保留選取供重試。刪除清除擴充功能的任務、對話紀錄、草稿及所屬暫存，保留原專案程式碼、成果包及已匯出檔案；外部、共用或無法證明權屬的 CLI 對話保留。發布結果不明或清理失敗時保留紀錄供核對，重新啟動只恢復清理。0.54.0 升級後請重新載入所有開啟此擴充功能的 VS Code 視窗，再使用刪除；舊 Host 或降版可能重新顯示已保留成果的舊紀錄。

窄視窗以任務抽屜保留主要對話空間，支援 Tab、Shift+Tab、Escape 及關閉後回到原按鈕。次要資訊收在詳情，待回答、錯誤及執行狀態保持可見。串流只批次更新選取中的對話，捲動位置每 250 毫秒保存，切換／關閉時補存最後位置；輸入草稿仍即時保存。

執行資訊顯示模型回報的計畫、Token、額度及工具狀態；無資料時標示未知。差異選單可查看模型回報快照，或開啟原生暫存／工作目錄比較，後者可能包含人工修改。檔案變更可直接開啟對應檔案。大量對話沿用虛擬化，Host 與 Webview 的歷史視窗各有 32 MiB 預算，卸載內容可重新讀取。

## 核對結果及執行上限

「核對任務狀態」只讀取已保存的回合、程序停止收據與發布標記，不呼叫模型，也不重送操作。執行、清理及發布分開呈現；缺少可靠證據時保留待核對狀態及執行鎖。程序關閉沿用一般任務 5 秒、工作流程 30 秒等待，再最多等待 5 秒終止確認。

單筆損壞紀錄不影響其他歷史的顯示；原件保留，畫面列出識別與修復入口，並暫停新派發。v1 紀錄仍可讀取，首次更新時原子升級並保留 `.v1-backup`；升級時請重載所有 VS Code 視窗。

使用者設定 `gitlabWorkspace.codex.maxConcurrentTasks` 預設 1，可選 2。本機各視窗共用執行槽，Repo、寫入目錄、安裝根、runtime 及 Git common directory 有交集的任務仍序列執行；同 Repo 的多個 worktree 也不會繞過互斥。等待某個資源的任務不阻擋其他獨立資源，排隊期間可調整本視窗的順序。

「自動核准本機操作」只處理符合任務範圍的命令與檔案修改。機器設定 `gitlabWorkspace.codex.autoApproveLocalOperations` 首次預設關閉；啟用後，新任務沿用偏好，任務可單獨覆寫並保存。Host 重開只恢復設定與狀態，仍須明確續作。額外權限、網路、問題、MCP 表單及登入繼續由使用者處理。診斷可先在編輯器預覽再另存，包含版本、狀態、能力、RPC 耗時、結束碼／signal 及有容量上限且已遮蔽憑證的 stderr 尾端；不保存原始提示詞。

## 隔離開發、交接與增量更新

新 Issue 開發與 MR 討論修正任務從該專案的管理快取建立獨立本機 Clone，只包含本次所屬的 Repo。Clone 使用獨立 Git objects、index 與 refs，不借用原 Repo 或共用快取的 Git metadata；本機複製不增加 Git Server 請求。原 Group／Repo 工作台可直接開啟任務檔案、差異與成果。既有 worktree 任務仍沿用原位置及驗證方式恢復，不自動搬移。本地 Wiki 永久保存於所屬工作區，GitLab Wiki 使用固定來源快照，兩者均不套用開發 Clone 的生命週期。

Issue 開發預設一般 Build，也可明確選擇 Build Auto。Auto 需要可用的同步子代理，且實際執行目錄的 sandbox 必須通過本機 `git add`／`git commit` 檢測。兩種流程都可先建立本機 Commit；Host 會檢查固定基準到 HEAD 的完整提交歷史，每筆新 Commit 標題須含該 Repo 的 `(#IID)`。乾淨工作樹可直接採用已核驗的提交，有剩餘修改才補 Commit。

最後驗證不依賴舊自動交付偏好，須取得同一成果版本的命令、cwd、時間及退出碼證據。在成果頁檢閱內容、提交與測試後，按「確認並交付」，Host 才普通推送並建立或重用自有 Draft MR、回覆 Issue。確認綁定內容、Commit SHA／訊息與測試證據，改寫提交或修改檔案後須重新確認。尚未送出遠端步驟的失敗交付可接續實作及重新驗證；已送出或結果未明時先對帳。目標分支前進會保留原驗證基準並列於 MR 說明，不自動 rebase；重用 MR 保留人工標題與描述，也不合併 MR、關閉 Issue 或解決討論。

準備時會核對 Git 身分與簽章設定；Clone 不整份複製原 `.git/config` 或 Repo-local hooks。團隊所需設定須在任務環境備妥；hook 改變成果時需重新驗證。GitLab 連結流程中的 Issue 開發只提供 App Server，沒有複製開發指令的備援入口。

MR 可選擇討論建立修正任務，固定來源／目標 SHA 與討論內容，在獨立 Clone 完成實作及測試。逐則回覆草稿可編輯並手動發布；送出前再核對版本，沿用既有標記去重與逾時對帳，並不自動解決討論。

GitLab Wiki 從專案預設分支的固定 SHA 快照建立草稿，來源保持唯讀，預覽後才逐頁發布。永久成果保存版本化的來源、頁面映射與發布收據，任務快照清理後仍可更新。一般 Repo 入口會尋找同帳號、站台、專案及分支最近已發布的來源；「依來源變更重新產生」也可從已保存成果接續。只有來源為已驗證後續版本、映射完整且變更都有對應頁面時，才重生受影響頁面與索引；舊成果缺少可靠映射或分支改變時，明示全量生成。Host 保護未選取頁面的內容，發布仍需重新預覽並核對逐頁收據；結果待核對時不清理來源。

## 原生目標模式與版本能力

已停止的自由任務可設定目標及 Token 預算，並選填執行時間預算；設定後由「接續」啟動。原生 Goal 可跨 turn 接續，完成、暫停或達預算時保留狀態；時間預算會中斷目前回合並核對程序收尾。它不取代 Issue／Reviewer 的既有成果門檻。

受管理任務以保存成果建立新任務，沿用新的準備與視窗接管流程。原生對話分支只供既有未受管理的自由對話使用，避免把任務的共用來源快取當成新的開發目錄。

進階能力依已捕捉的 CLI 契約啟用；對話分支、Goal、共用 Skills 與用量介面支援已驗證的 0.166.0、0.167.2。原生對話刪除在 0.167.2、0.169.0 啟用；0.169.0 不因此取得其他未驗證的進階能力。缺少能力時保留成果與未完成清理狀態。其他版本維持基本相容行為。開發者可用 `scripts/generate-codex-protocol.mjs --codex <原生執行檔完整路徑>` 重建原 0.166.0 型別；0.167.2 的增量及 0.169.0 核准／刪除契約另存於測試 fixture。

Wiki、合併審查、上版檢查及 BMAD 頁面的「使用 Codex 執行」會帶入目前表單與已核對的專案根目錄。任務建立後會切到工作台的「Codex」頁，集中顯示執行訊息、命令與檔案變更、對話、核准、暫停及恢復。也可從命令選單執行「GitLab Workspace: 開啟 Codex」。

左側列出任務，中央分成「執行紀錄」與「成果」，「任務詳情」收納模型、用量、核准範圍與診斷。窄版使用任務選擇器。待回答區與輸入框保留在分頁外，背景事件不切頁或移動焦點。回覆、報告與 Wiki 可閱讀 Markdown，Wiki 另有原文及差異；程式碼可複製，檔案連結經 Repo 範圍核對後開啟對應行號。

若需要回到執行與成果同頁的排列，可在 VS Code 設定把 `gitlabWorkspace.codex.workspaceLayout` 從預設 `workspace` 改為 `classic`。切換立即生效，保留草稿、選取任務及待回答內容，不會重新啟動或重送工作。這是版面回退開關：兩種排列共用同一個準備頁、任務控制、收據及資料保護；不恢復舊版後端或原生建立精靈。改回 `workspace` 即恢復分頁工作台。

歷史與即時輸出合併更新，長工具輸出可展開。位於底部時跟隨新訊息，往上閱讀時保留位置，可按「回到最新」；「讀取更早的對話」會補入較早紀錄。

## 第一次使用

1. 安裝 Codex CLI 0.165.0 或更新版本，並信任 VS Code 工作區。
2. 在「工具與環境」的「Codex 執行環境」按「檢查 Codex」。Windows 需要可用的 Codex sandbox；尚未登入或設定完成時，使用畫面的登入及設定入口。
3. 安裝此專案對應的 WorkflowKit，並在功能頁填妥參數，按「使用 Codex 執行」。

預設從 VS Code 的 PATH 尋找相容的 Codex，支援官方 npm 安裝。若找不到，於使用者設定填寫 `gitlabWorkspace.codex.executablePath` 的完整路徑；工作區設定不會覆寫此執行檔。Provider 與既有帳號沿用本機 Codex，登入由 Codex 自行保存及更新。一般任務預選沿用本機設定，審查預選 Luna 的固定預設強度；建立前可依模型清單及套件能力修改。

## 從 GitLab 工作直接啟動

以下入口需要已登入 GitLab、已安裝的 WorkflowKit，以及支援共用 Skills 的 Codex CLI 0.166.0+。多份本機副本會在準備頁選擇；沒有副本時由 Host 準備該專案的管理快取，不需要先手動 Clone 整個 Group。既有 Skills／BMAD 的獨立操作入口保留。

### 從 Issue 開發

在 Issue 預覽或詳情按「使用 Codex 開發」。任務保存當下的標題、描述、標籤與版本，從 GitLab 提供的預設分支固定 SHA，在獨立本機 Clone 建立 `issue/<iid>-<slug>` 分支，再由 BMAD 實作與測試。本機原 Repo 的未提交內容不帶入任務，也不會被修改。

單純產生規格不算開發完成，會先接續實作。Host 會檢查實際差異及核定檢查命令的退出碼，實作與驗證合計最多三輪；仍未符合完成條件時顯示「尚需接續」。任務明確回報現有程式已滿足需求且核定檢查均通過時，可在沒有差異的情況下完成，不建立空 commit／MR。沒有設定自動檢查命令的純文件變更，可由使用者檢閱差異後明確人工驗收；包含程式變更時仍須實際檢查。Issue 原頁可查看任務及差異。準備、排隊及執行使用同一來源快照；「重新檢查」才同步目前來源，版本差異須明確確認。

### 建立專案 Wiki

在 GitLab 專案列或已對應專案的本機 Repo 列按「產生 GitLab Wiki 草稿」。Host 會取得遠端預設分支 SHA，以 `git archive` 建立隔離快照。Codex 的執行與寫入目錄為快照中的 `wiki/`，來源檔案不列入寫入範圍。

草稿完成後，在任務視窗檢查來源、頁面清單與內容；更新頁面可展開目前 GitLab 內容。確認後按「發布至 GitLab Wiki」，Host 才執行新增或更新。生成頁面放在 `codebase/`，保留其他頁面；Wiki 連結及程式來源引用會轉成 GitLab 連結。頁面內容改變後需重新預覽，部分成功及每頁收據會持續保存。此 GitLab Wiki 流程只提供 App Server 執行。

發布逾時不會自動重送。先按「重新預覽／核對結果」讀取 GitLab；已找到相同內容時會完成對帳。仍不確定時，須先在網站人工核對，再使用「確認後允許重試」。結果未明時不可刪除或接續修改這份任務。

### 一鍵 MR 審查

在 MR 詳情按「一鍵 Code Review」，選擇 MergeReviewer 或 ReleaseReviewer。Host 取得來源與目標版本，從已驗證 remote 同步必要 MR ref（含 fork），建立固定審查 refs，再交給所選 Reviewer。兩種工具各自保存 request、runtime、報告及恢復紀錄。原生報告完成後，MR 的審查報告分頁會讀取全文並填入空白留言草稿，保留既有草稿。

使用「作一般留言發布」前會再次核對原任務、帳號、來源及目標 SHA；版本改變時需重新審查。過長報告可保留完整版，將留言草稿整理為 50,000 字以內。手動選擇 Repo／分支的既有入口仍可使用。

## Reviewer 固定設定與完成檢查

建立審查任務時選擇固定模型及強度；每個 turn/start 都明確傳入該設定。Auto 已移除，既有 Auto 偏好在準備頁改選有效固定值。複製提示詞沿用 CLI 當前設定，由目前 agent 直接審查。

回合結束後，Host 核對原生 request 與發布收據。尚未發布且有保存進展時沿同 thread 接續，最多兩次；無進展則保留待續。已發布但有必要缺口的報告仍可開啟，狀態顯示尚有缺口。歷史 routing request 在核對固定身分後沿最後保存強度續作，不重 capture。

診斷保存派送模型／強度、thread／turn、送出及結束時間；服務回報的模型另行保存，未回報時保持未知。它不以路由紀錄或模型自述證明實際服務端設定。

## 執行與互動

同一實體專案根目錄的任務依序執行，其他視窗共用同一把執行鎖。排隊任務開始前會再次驗證專案及 Skills；環境已改變時需回功能頁重新確認。執行中會阻擋同根目錄內由本擴充功能管理的套件更新、下載／同步及 Git 寫入操作。

Host 讀取實際執行 cwd 的有效 Codex 設定，沿用核准政策與 reviewer，以任務寫入範圍及無網路 sandbox 執行；read-only 設定仍保持唯讀。任務保留原 Group 的 AGENTS 與 Skills 安裝根，Repo 規則由固定版本的工作目錄載入，每階段只明確載入必要的完整 Skill 指引。Codex 自動提供的技能簡介仍可能存在。核准 UI 呈現原生支援的選項及範圍；GitLab 連結流程不接受模型擴大網路權限或直接執行 Push／GitLab 發布，測試依賴須先由 Host 或使用者備妥。

「傳送」可在執行期間補充要求，或在本輪結束後接續同一個對話。「暫停」只影響選取任務：排隊任務移出佇列，執行中任務中斷 turn 並清理所屬程序，保留原生審查的 request、快照、草稿及已完成操作。確認程序停止後才顯示「已暫停」，其他排隊任務可繼續。「恢復」沿用原對話與審查 request ID，先核對進度再開新回合接續，並重新驗證原專案及 Skills。明確「取消」才將原生 request 設為取消，不能再自動恢復。

新任務的執行 Host 位於原 Group／Repo 視窗；其他 VS Code 視窗只讀取任務狀態及保存成果，執行中的問答、停止、接續與發布都回原視窗操作。舊版獨立任務視窗仍沿用原歸屬：即使任務已暫停，原 Group 視窗也不直接接管；重新開啟舊任務視窗後，須先核對前一程序已停止，再取得新的執行代次。只關閉或重開工作台面板時，仍由其執行 Host 持續監聽。

「刪除連線並保留成果」先阻止新操作、停止所屬程序，再將成果存到 runtime 外的永久成果區，驗證可還原後才清理。只刪除有建立紀錄且沒有其他任務引用的原生對話、草稿、診斷、備份、來源快照、任務 Clone／舊 managed worktree，以及名稱與 SHA 符合的臨時 refs。Clone 的未推送提交資料也須先保存。原 Repo、使用者工作目錄、共用 Repo 快取、BMAD 持久成果與共用安裝保留；其他 Wiki 任務需要的種子先轉存。

清理先保存 closing 狀態及最小 journal，退休後保留防回寫 tombstone。獨立視窗任務使用 v4 紀錄及 owner／generation 核對，舊 v1／v2／v3 任務繼續依原契約讀取與恢復；清理 journal 使用 v2。升級時需重載所有視窗，舊 Host 會拒絕管理 v4 任務。遇到占用、路徑重新導向、程序停止或發布結果不明時保留原資料待核對。封存後保留可開啟成果的最小工作區指標，移除啟動檔中的完整原始提示；不會從舊工作區重新派送。尚未回答、尚未送出或 Goal 未完成時，不自動清理；Group 文件完成後也保留至確認處理或明確交接。

## Group 需求分析與人工備援

在本機 Group 的專案工具列選「需求影響分析」，輸入異動需求並選擇 Repo。預設使用該 Group 的 Repo，不納入其他開啟工作區；不需登入 GitLab。分析使用各 Repo 已提交 HEAD 的 archive，排除 dirty／untracked 內容。已備齊來源不呼叫 Git Server；缺少 promisor、LFS 或 submodule 內容會明示缺口。快照容量或檔案數超限時停止，不截斷資料。

先以 Codebase LLM Wiki 的 source-first 功能探索查證來源，再按需載入 BMAD Spec；不需預先建立 Wiki。文件保存在任務成果目錄，包含 `SPEC.md`、`cards.md`、`sources.json`、`issues.json`，並透過原 Group 的持久索引供後續任務查閱。Host 核對固定 SHA、來源 inventory、證據檔案及草稿版本；「檢閱並建立 Issue」可選擇牌卡，逐張保存發布收據，未知結果先對帳。手動複製只產生文件與草稿，由人工開卡。

「轉交人工處理」停止自動工作與後續發布。成果包包含文件、需求／Skills／待辦摘要、測試證據、基準及交付 SHA、完整二進位 patch、新增／刪除與 mode／hash 清單、發布收據及新的接續指引。可還原到新的人工 worktree，使用新 CLI 對話接續；該目錄由使用者管理，不受原任務清理影響。還原需保留原 Repo 及基準 commit；Repo 不存在時仍可閱讀、複製及匯出文件。

完整成果上限為 128 MiB／50,000 個檔案。變更含不支援的 symlink／gitlink、缺物件或實際還原驗證失敗時保留原任務 Clone／worktree。發布結果未明時可匯出明確標示 `provisional` 的接手包，列出待核對操作，但不授權刪除原環境，也不盲目重傳附件。「重試交付」仍會核對目前成果；版本未變時依收據接續，版本已變時須重新檢閱及確認。

成果封存後介面改為唯讀，不讀舊 thread，也不能接續或發布舊任務；「以成果建立新任務」使用新 ID。登出或切換帳號後，可從「管理本機連線」的原生選單停止、清理或匯出原任務；閱讀及匯出成果不需要啟動 App Server。VS Code 執行期間須保持開啟，關閉工作台不影響任務。

App Server 由建立它的操作管理，任務、環境檢查、模型清單與歷史讀取結束時會停止所屬程序；借用執行中任務連線的讀取不會關閉該連線。停止收據在所有相關鎖、排程與保存狀態完成更新後清除。Wiki 來源壓縮包解開後即清理，續作需要的來源快照則保留到刪除對話。

WorkflowKit 安裝包用畢清除；已知安裝根目錄仍使用的版本驗證工具保留，升級或移除安裝後回收不再需要的工具。清理會避開其他視窗正在使用的附件。安裝包清除後，再次安裝需要連線下載，既有版本的離線狀態檢查仍可使用保留的驗證工具。舊版 globalStorage 日誌只清理可辨識且未變動的格式，現在的原生日誌由 VS Code 管理。

## Auto-Accept

「自動核准本機操作」首次預設 OFF；啟用機器偏好後，新任務沿用，單一任務可另行開關。開啟後只接受任務範圍內的單次命令與檔案核准，不新增永久規則。額外權限、網路權限及明確的 `git push`／`glab` 發布要求不會自動接受，也不能透過一般核准取代成果確認。一般問題、方案選擇、MCP 表單與登入仍由你回答。

開啟時也會處理當下等待中的支援核准，同一要求只回覆一次；關閉或暫停立即阻止後續自動回覆。切換頁面、暫停、恢復及重新載入會保留任務設定；重新開啟不會自動開始模型工作。自動回覆失敗時會保存關閉狀態並提示手動核對。

時間線中的「已自動核准」表示核准已送出，操作結果仍依命令及任務狀態判定。Log 僅記錄必要任務、thread、turn、request 識別與核准範圍，不保存完整命令或提示詞。此功能在本擴充功能直接處理 App Server 核准，無須另外安裝終端版 Auto-Accept。

輸入草稿依 Host 的任務 ID 保存至 Webview state，切換任務與重建畫面均可還原。Host 確認接受或已排隊後，才清除本次送出的草稿版本；送出後繼續編輯的文字保留。blocked、failed、cancelled、unknown 均保留內容；unknown 必須先核對，不能自動重送。

「前往待回覆要求」將焦點移至目前任務的核准或回答表單；「跳至最新回覆」與「複製回覆」協助閱讀完整內容。串流不逐字播報，由獨立 polite 摘要通知完整回覆及狀態變更，背景事件不移動焦點。

## 完成、報告與恢復

「本輪完成」表示 Codex 已結束這一輪工作。合併／上版審查的報告、完整性與缺口仍以既有本機審查紀錄為準；BMAD 進度依已保存文件判斷。

進行中或可修復的審查提供「使用 Codex 恢復審查」，保留原 request ID、固定證據及 checkpoint。已終止的 request 只供檢視診斷；已發布時開啟既有報告，只有清理未完成時提供重試。「使用 Codex 重新同步」建立新的 request ID，不覆寫舊報告。

支援新啟動介面的套件會在準備任務時保存固定輸入檔，摘要與啟動命令使用同一份路徑及分支。執行前核對檔案摘要與已安裝 helper；輸入已變更時重新準備，不把既有 request 改成另一份審查。新 helper 的狀態及能力檢查使用唯讀入口；舊套件仍按其宣告的介面執行。

證據操作的完成數和語意審查待完成數分開顯示。後者是最近一次 `check` 保存的結果，不隨閱讀自動歸零。正式審查若尚有可取得的必要證據，先依 checkpoint 續查；同強度的自動修稿最多兩次，無進展的相同 checkpoint 不重跑。到達回合上限時保留待辦以供恢復，不把上限寫成證據缺失或審查完成。

關閉或收合工作台不停止任務。關閉 VS Code 會中斷工作；重新開啟後，可讀取對話，再手動續作。中斷後會先核對歷史與產物，不自動重送原始工作。結果未明或無法確認程序樹已停止時，狀態顯示「結果待核對」並保留執行鎖。

任務輸入、thread／turn ID 及收據存於本機擴充功能儲存區；完整對話由 Codex 保存，可分頁讀取。這些紀錄不寫入業務 Repo，偵錯日誌也不保存完整提示詞或認證內容。

## 開發驗證

`npm test` 包含離線協定、任務生命週期、原有功能、Webview、Extension Host 與打包驗證。一般測試不會呼叫模型。

真實 Codex 驗證另以 `npm run test:codex:live` 執行。程式會新建 `gitlab-codex-real-*` 暫存目錄、安裝固定 WorkflowKit group fixture，並建立獨立測試 Repo、VS Code 設定檔及擴充功能目錄。可用 `--vsix <安裝包>` 指定候選包。此驗證使用目前 Codex 帳號呼叫模型，操作打包後的真實 Webview，並保存 Wiki 查詢、三種 Reviewer 與 BMAD 的任務結果與截圖至 `.tmp/codex-live-*`。這個 fixture 不驗證真實 GitLab 的 Issue 開發、MR 討論修正或遠端發布；需另行驗收。

Live fixture 只會核准白名單中的唯讀 Git 命令，且須核對原始要求的執行目錄正好是 fixture 根目錄或其 `service` Repo。額外權限、檔案寫入核准、網路或其他未列出的要求會取消並令驗證失敗，交由人工審查；不以命令文字是否包含網址判定安全。Auto-Accept 開關只在已暫停並確認清理後測試，恢復前保持關閉。主要 GitLab 工作流程的端到端驗收仍需明確指定測試專案及遠端／模型呼叫授權。

通訊以 [官方 Codex App Server 協定](https://learn.chatgpt.com/docs/app-server)的 stdio 模式實作，首版測試基準為 CLI 0.165.0。CLI 不相容、未登入或環境未完成時，需求探索／Issue 文件及 MR 審查仍可複製提示詞至 CLI 或 VS Code Codex 聊天；由人工處理最終產出。GitLab Wiki 與 Issue 開發須先修復 App Server 環境。
