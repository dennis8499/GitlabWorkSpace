# 疑難排解

## 無法連線或驗證 Token 失敗

- 確認輸入完整 GitLab 網址，使用 `http://` 或 `https://`，並包含自架站台需要的連接埠及安裝路徑。
- 確認 Token 尚未撤銷、具有 `api` 範圍，且帳號可存取目標群組。
- Token 只有在 `GET /user` 驗證成功後才會儲存。修正網址或 Token 後，重新執行 **GitLab Workspace: 連線 GitLab**。
- HTTP 不會加密 Token 傳輸，建議改用 HTTPS。

## 沒有看到群組或專案

- 確認帳號已加入預期群組，再從工作台上方重新選擇群組。
- 展開子群組並確認其中有專案；專案頁會列出所選群組及其子群組。
- 執行 **GitLab Workspace: 重新整理工作台**。
- 若 GitLab API 拒絕要求，依錯誤訊息檢查 Token 範圍、帳號權限及連線狀態。

## 「我的工作」沒有 Issue

預設清單只顯示目前帳號被指派的未結案 Issue。確認群組、指派對象、狀態及清單篩選條件。清除搜尋或篩選後再重新整理；若新建 Issue 沒有指派給自己，它仍會立即開啟在詳情頁，但不會加入預設清單。

## 找不到 Repo 或下載／更新失敗

- Clone 前請先選群組，並到工作台設定為該群組選擇本機工作目錄。閱讀和討論 Issue 不需要本機目錄。
- 確認 Git 已安裝；在終端機執行 `git --version`。若找不到 Git，將 Git 加入 `PATH` 後重新啟動 VS Code。
- 確認帳號具有專案讀取權限。複製私有專案需要可存取該專案的 GitLab Token。
- 開啟專案頁的操作結果區，查看各 Repo 成功、略過或失敗的原因。

開始前會檢查整批 Repo 的資料夾與 origin。既有目錄必須是對應的 Git Repo，且 origin 必須符合 GitLab 專案的 HTTPS 或 SSH URL；一般資料夾、其他 Repo、符號連結或名稱重複會讓操作停止。有本機修改、未追蹤檔案或分支分歧的 Repo 會略過，其他 Repo 仍會處理。

## 側欄或版控工作台沒有 Repo

- 確認已在 VS Code 開啟本機 Git Repo 根目錄；多資料夾工作區會列出每個由 VS Code Git 偵測到的 Repo。
- 在擴充功能檢視確認 **Git**（`vscode.git`）已啟用，再按版控頁的 **重新整理**。
- 使用桌面版 VS Code 1.90 或更新版本，並確認 Git 2.30+ 可供 VS Code 使用。Git 版控可離線使用，不需要先連線 GitLab。

## Git 操作失敗或結果不確定

- 檢查目前選取的 Repo、分支、工作目錄變更與錯誤訊息；重新整理後確認狀態再決定是否重試。
- HTTPS／SSH 認證沿用 VS Code Git 與作業系統原有的認證方式。GitLab 權杖只會用在 remote 已確認對應目前 GitLab 專案時。
- Force Push 若回報遠端 SHA 已變更，先 Fetch 並檢查提交歷史；不要直接重送舊的 Force Push。
- Amend、Reset、捨棄檔案和改寫歷史前會建立復原 ref 或 Stash。可在左側 **復原點** 或 **Stash** 區塊檢視與還原。

## 操作後 Git 指令持續執行

版控的背景快照不會再次呼叫 Git status，內容不變的 status 通知會直接略過，真正的變更才會合併為有限次更新。相同檔案或提交連點共用讀取。隱藏工作台會取消尚未開始的畫面工作，已開始的寫入會正常完成。

若仍持續看到 Git 活動，可檢查工作台後臺的 Git 操作紀錄，並對照 VS Code 的 **輸出 → Git**。前者記錄擴充功能操作，後者也包含 VS Code 自動 Fetch、檔案監看及其他 Git 擴充功能的活動。確認是哪一個來源持續觸發後，再檢查相應設定或錯誤。

## Merge 或 Rebase 衝突

在衝突清單按 **開啟 Merge Editor**。若 VS Code Merge Editor 無法開啟，工作台會提供原生文字編輯器。儲存解決內容後按 **標記已解決**，再依操作類型按 **繼續**、Rebase 的 **略過** 或 **中止**。互動式 Rebase 的 GUI todo 狀態會保留在 Repo 的 Git metadata 中，重啟 VS Code 後仍可繼續。Stash 套用衝突不會刪除原 Stash；解決並暫存後可在清單再次 Apply。

超過 1 MiB 的 Diff 會顯示原生 Diff 入口；二進位檔仍可在變更清單使用整檔暫存或取消暫存。

## 開發與交付入口不可用

Issue 可閱讀與討論，但本機開發需要讓 VS Code 工作區符合該 Issue 所屬 Group，並先下載對應 Repo。單一 Git Repo 會以 remote 對應目前 Group；若工作區無法唯一辨識，請在 VS Code 開啟 Group 資料夾或調整多資料夾工作區，再重新整理工作台。工作目錄不從舊儲存值回復，也無法在工作台手動指定。

交付操作依序進行差異預覽、Commit、Push、建立 MR。若某階段失敗，查看 **開發與交付** 分頁中的錯誤與階段狀態，再重試該步驟。若 Git 工作目錄含有未完成的本機修改，先自行檢查後再繼續。

若無法交接 Megin work，請確認 Work ID、核准 Repo 清單及 Group 根目錄與任務一致，再重新載入原交接證據。遠端 Push 或 MR 回應不明時，先檢查 GitLab 上的實際結果，再使用已保存的 commit 繼續；避免建立重複 MR。

## Issue Board 或關聯圖未載入

請確認帳號可讀取目前 Group 的 Issue Board，並按 **更新資料** 重試。若圖譜只有部分節點或關係，工作台會保留已成功取得的 Issue 並提供重試按鈕；改回清單模式仍可瀏覽已指派 Issue。

## 舊草稿找不到或未恢復

舊版建立的 Issue 草稿仍保留在 VS Code Webview 狀態，但新版 **分析** 頁已改為 Codebase LLM Wiki 功能指南，不會顯示或發布這些草稿。若需檢查或發布舊草稿，請使用具備舊草稿介面的相容版本；切換前避免清除 Webview 狀態。

若切換群組或帳號後看不到草稿，請先回到建立草稿的執行個體、帳號及群組。仍找不到時，請避免在猜測的目標上重新建立內容，先確認原本草稿所屬專案。

## Issue 功能或欄位不可用

編輯、留言、移動、複製、刪除、子工作、開始日期和討論串解決等功能會依 GitLab 權限、版本及 API 能力顯示。詳情頁的載入提示會指出部分資料不可用；重新整理後仍失敗，請按畫面錯誤訊息檢查群組、專案存取權與 GitLab 服務狀態。

## 工時登錄狀態不確定

若送出後未收到 GitLab 確認，工作台會先保留為待對帳紀錄，不會自動重送以避免重複登錄。切換到 Issue 的 **工時** 分頁查看待送出紀錄及 GitLab 工時；確認 GitLab 是否已建立紀錄後，再決定重試或完成對帳。
